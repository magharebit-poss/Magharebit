# License generation: how a license is issued and verified

Operational summary for the team. The normative POS-facing spec is [`pos-license-contract.md`](pos-license-contract.md); this page explains who issues what, and where Ed25519 comes in.

## Short answer

There are **two separate artefacts**, and only the second is signed:

| | License **key** (v1) | License **token** (v2) |
|---|---|---|
| Looks like | `MGH-202610-234EC341-3667-C4` | a JWT (`eyJhbGciOiJFZERTQSIs…`) |
| Created | when an admin (or the self-signup) issues a license | when a POS terminal **activates** the key |
| Purpose | a typable handle the merchant enters once | proof of plan, expiry and terminal binding |
| Cryptography | random id + HMAC-SHA256 checksum (server secret) | **Ed25519 signature (EdDSA)** by the server's private key |
| Verifiable offline by the POS | **No** (shape check only) | **Yes**, with the public key from `/api/licenses/jwks` |

So: the admin console does **not** sign anything when it issues a license. It creates a license record and a key. The Ed25519 signature is applied later, by the server, when the POS exchanges that key for a token. The token is what the Tauri POS verifies offline.

## 1. Issuing a license (admin console and sign-up)

Every path writes one document in the MongoDB `licenses` collection: `id`, `key`, `merchantId` (phone or email), `plan`, `issuedAt`, `expiresAt`, `status`, optional `isTrial`, and later `terminals[]`.

| Path | Who | Route | Audit action |
|---|---|---|---|
| Merchants page → drawer → "Generate license" (plan + 1/3/6/12/24 months) | owner, operator | `POST /api/licenses` | `generateLicense` |
| Merchants page → approve a pending merchant | owner, operator | `POST /api/admin/merchants/[id]/approve` | `approveMerchant` + `generateLicense` |
| Leads page → activate a lead (creates the merchant + license) | owner, operator | `POST /api/admin/leads/[id]/activate` | `activateLead` + `generateLicense` |
| Self-service sign-up (OTP) → automatic 14-day trial (Starter limits) | the merchant | `POST /api/auth/complete-signup` | (none, not an admin action) |

The key is generated by `generateLicenseKey()` in `src/lib/license-key.ts`:
`MGH-{YYYYMM}-{8 hex random}-{4 hex random}-{2-char checksum}`. The checksum is HMAC-SHA256 of the body with `NEXTAUTH_SECRET`; it only lets the server reject mistyped or invented keys early. It is not a security control on the POS (the POS never has the secret). Issuance fails closed if `NEXTAUTH_SECRET` is missing.

Later admin actions on the same record: extend, revoke, suspend/reactivate the merchant, free a terminal slot. All are audited and take effect at the POS's next online refresh.

## 2. Activating a terminal: where Ed25519 signs

1. The merchant types the key into the POS. The POS sends `POST /api/licenses/activate` with `{ key, machineId }`.
2. The server looks up the record (expired, revoked, suspended merchant → refused) and registers the `machineId`, enforcing the plan's terminal limit atomically (`terminal_limit` when full).
3. The server builds the claims (`plan`, `trial`, `exp` = end of the paid period, `refreshBy` = now + 7 days, `maxRegisters`, `maxBranches`, `features`, `machineId`, …) and **signs them with Ed25519** using `LICENSE_SIGNING_PRIVATE_KEY` (`src/lib/license-token.ts`).
4. The POS stores the token and verifies it **offline** with the public key (`GET /api/licenses/jwks`, also bundled in the POS build): signature, `alg` = EdDSA, `kid`, `iss`, `aud`, and that `machineId` matches its own device. A copied token is useless on another device.
5. The POS refreshes online through `POST /api/licenses/validate` at least every 7 days (new token, later `refreshBy`). Offline it keeps working until `refreshBy + 72 h`. At `exp` it goes read-only, with no grace.

The private key exists only in the server's secret store, never in the repo or the POS. Generate one with `node scripts/gen-license-keypair.mjs <kid>`; rotation adds a new `kid` to the JWKS while the old one stays until its tokens expire.

## 3. Current status (be precise when communicating this)

- **v1 is live**: key + online `validate`, with the POS caching the answer (72 h grace).
- **v2 is implemented and tested on this branch** (`license-token-unit.mjs` 28 checks, `license-v2-e2e.mjs` 63 checks) **but not live**: until `LICENSE_SIGNING_PRIVATE_KEY` / `LICENSE_SIGNING_KID` are set in the production environment, `/api/licenses/jwks` and `/api/licenses/activate` answer `503 v2_not_configured` and nothing is signed.
- **POS side is not verified from here.** Offline verification in the Tauri POS is the POS team's implementation, built against the test vector in the contract (section 6). The open points in contract section 7 (Ed25519 support in the runtime, stable `machineId` per platform, 7-day refresh) are theirs to confirm.

## Go-live checklist for v2

1. Generate the production key pair and store the two printed values in the Vercel secret store.
2. Check `GET /api/licenses/jwks` answers 200 with that `kid`, and `POST /api/licenses/activate` returns a token for a test key.
3. Ship the JWKS in the POS build as the fallback key set, then switch the POS from v1 to v2.
