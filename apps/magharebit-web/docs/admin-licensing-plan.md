## 2. Gaps and defects found

1. **The key is not cryptographically signed.** The checksum is 8 bits, so 1 in 256 random strings passes it. Expiry cannot be verified offline, because the key carries no expiry.
2. **Hard-coded fallback secret:** `license-key.ts` uses `'fallback-dev-secret'` when `NEXTAUTH_SECRET` is unset. Anyone can then compute valid checksums. This contradicts the fail-closed rule in `admin-auth.ts`. It should fail closed (throw) in production.
3. **No audit trail.** `approvedBy` is the literal string `'admin'`.
4. **Missing features:** extend subscription, status toggle (Active/Suspended without revoking), coupons, broadcast notifications, shop-type tags, sidebar shell.
5. **Product conflict:** the site promises "14-day free trial, no card", and signup activates it automatically. Your brief says accounts stay PENDING until an admin generates a key. Both cannot hold for trials (decision D1).

## 3. Proposed architecture

### 3.1 License model (recommended: hybrid, decision D2)
- Keep the short typable key (`MGH-…`) as the handle the merchant types or pastes. It remains valid, so existing keys keep working.
- Add a **signed entitlement** (Ed25519) returned by `POST /api/licenses/activate` and by `validate`. The POS verifies it **offline** with an embedded public key.
- Signing is **integrity, not encryption**: the payload is not secret, and encrypting it adds nothing the signature does not already give.
- Private key: env var `LICENSE_SIGNING_PRIVATE_KEY` (server-only), with a `kid` for rotation. Public keys are published at `GET /api/licenses/public-keys`. Generated by a one-off script and **never committed**.
- Payload, endpoints and POS behaviour are in `docs/pos-license-contract.md`.

### 3.2 Data (new MongoDB collections; extend `merchants`)
- `admin_users`: `{ username, displayName, role: owner|operator|viewer, passwordHash (scrypt), createdAt, disabledAt? }`
- `audit_logs` (append-only; no update or delete routes): `{ ts, actorId, actorName, action, targetType, targetId, meta, ip, requestId }`
  - Actions: `generateLicense`, `revokeKey`, `extendSubscription`, `approveMerchant`, `suspendMerchant`, `reactivateMerchant`, `createCoupon`, `broadcastNotification`.
- `coupons`: `{ code, kind: percent|free_months|trial_days, value, plans[], maxRedemptions, redeemed, validFrom, validUntil, active, createdBy }`
- `notifications`: `{ title{ar,fr,en}, body{ar,fr,en}, audience: all|plan|shopType|merchantIds, channel: portal|whatsapp, createdBy, sentAt, counts }`
- `merchants`: add `shopType` (`epicerie|cafe|boulangerie|restaurant|other`, mapped from the existing free-text `sector`) and `suspendedAt?`. Plan = tier (Starter/Business/Enterprise, already present).

### 3.3 API (all admin routes require an admin session and write an audit record)
- `POST /api/admin/licenses/generate` (merchant, plan, duration or trial days, optional coupon)
- `POST /api/admin/licenses/[id]/revoke`, `POST /api/admin/licenses/[id]/extend` (months|days, reason)
- `PATCH /api/admin/merchants/[id]/status` (`active|suspended`; suspended makes `validate` return `suspended` without destroying the license)
- `GET|POST /api/admin/coupons`, `GET|POST /api/admin/notifications`, `GET /api/admin/audit-logs` (filters: actor, action, target, date)
- `POST /api/licenses/activate`, `GET /api/licenses/public-keys`; `validate` stays backward compatible and gains an `entitlement` field.

### 3.4 UI (decision D3: I need the Wayloz reference)
- `/[locale]/admin` shell: sidebar (Merchants, Licenses, Leads, Coupons, Notifications, Audit log), RTL-aware, existing pine/gold tokens.
- Merchants table: filters (status, shop type, tier), Active/Suspended switch, shop-type chips, tier control, "Generate license" and "Extend" actions.
- Licenses, Coupons, Notifications and Audit tables with filters and pagination.

## 5. Risks and guardrails
- **Security review:** license signing and verification is security-sensitive. I will draft it, but the repo's AI-governance table asks for human review of security controls. Treat the crypto module and key custody as needing senior sign-off before production.
- **Key custody:** the signing key must live in the host's secret store. Losing it blocks new licenses; leaking it allows forgery. Rotation uses `kid` and keeps old public keys.
- **Revocation vs offline:** a signed entitlement cannot be revoked while a device stays offline. Mitigation: short refresh window plus the existing 72 h grace (see contract).
- **Brute force:** `validate` and `activate` need real rate limiting. The current in-memory limiter does not work across serverless instances, so a shared store or an edge rule is needed.
- **Migration:** v1 keys keep working. No bulk re-issue.
